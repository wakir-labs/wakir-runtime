# Wakir Identity Substrate — Specification (Phase 1a)

This document specifies the persona-identity primitives used by the
Wakir runtime in Phase 1a: hierarchical key derivation across two
elliptic-curve axes, persona-binding documents (DID + AIP), cold-storage
of the persona seed, and signature formats for the two document types.

It is the user-facing companion to the implementation under
`wirelang/identity/` and the Phase-1a Cross-Review Zone 1 consensus
marker (D-2: 2-of-3 SLIP-39 cold-storage default).

Audience: implementers and operators. The text follows the Wakir
brand-guide §9 convention: persona role-strings, never personal names,
in all examples.

## 1. Two-curve stack

A Wakir persona is rooted in a single 64-byte seed (BIP-39-derived in
production). From that single seed, two master keys are deterministically
derived along two parallel axes:

| Axis | Curve | Master derivation | Purpose |
|---|---|---|---|
| 1 | secp256k1 | BIP-32 (`HMAC-SHA512` with key `"Bitcoin seed"`) | DID verification methods, OTS-anchor signatures, treasury wallets |
| 2 | Ed25519 | SLIP-0010 (`HMAC-SHA512` with key `"ed25519 seed"`) | Biscuit authority/append-block signatures, AIP `biscuit_root_pubkey` |

Sub-keys for spawned sub-agents are derived along the path

```
m / 44' / WAKIR_COIN_TYPE' / persona_idx' / spawn_counter'
```

with all four levels hardened on both axes. SLIP-0010 mandates hardened-
only derivation for Ed25519; we mirror the convention on secp256k1
to keep the operational model symmetric.

`WAKIR_COIN_TYPE` is the constant `0x57414B49` (ASCII `WAKI`); it lives
inside the BIP-32 hardened-index range and is treated as an internal
sentinel until/unless Wakir registers a coin type with SLIP-0044.

Test-vector conformance (verified in
`wirelang/tests/test_identity_key_derivation.py`):

- BIP-32 test vector 1 (`seed = 000102030405060708090a0b0c0d0e0f`):
  master matches `e8f32e72…6b35`.
- SLIP-0010 ed25519 test vector 1 (same seed): master matches
  `2b4be7f1…b19e7`.

## 2. Persona-binding documents

Two documents are produced for each persona:

### 2.1 DID document (`did:web`)

Generated by `generate_persona_did_document`. Carries both verification
methods (secp256k1 and Ed25519), uses the `did:web:wakir.dev:personas:<role>`
identifier, and is published under

```
https://wakir.dev/.well-known/did/<role>/v<N>.json
```

The version segment `v<N>` is a Wakir convention (B2 of the consensus
marker) so DID-document rotations are explicit and the historical
versions remain individually addressable.

### 2.2 AIP document

Generated by `generate_aip_document`. Conforms to
`draft-prakash-aip-00` §2.3 (required fields `aip`, `id`, `public_keys`,
`name`, `delegation`, `protocols`, `document_signature`, `expires`)
and adds the Wakir `biscuit_root_pubkey` extension that points at the
Ed25519 root used to verify Biscuit-token authority blocks issued
under this identity.

The AIP-document is bound to its DID-document via
`verification_methods[].controller`, which carries the un-versioned
DID URI.

## 3. Cold-storage of the persona seed (SLIP-39)

The persona seed is the single recovery surface for both curves. Loss
of the seed is unrecoverable; theft of the seed is a full persona
compromise. We therefore split the seed at issuance time using
SLIP-39 Shamir secret sharing.

### 3.1 Default: 2-of-3 (Phase 1a)

Per ADR-0023b §3 and Cross-Review Zone 1 consensus marker D-2, the
Phase-1a default is

- `shares_n = 3`
- `threshold_t = 2`

This is implemented as a single SLIP-39 group with one (T, M) tuple
`(2, 3)` and `group_threshold = 1`. Three mnemonic shares are issued;
any two reconstruct the master.

Operational guidance:

- Each share is an independent physical artefact (paper, metal plate,
  encrypted USB). Shares MUST be stored in geographically separated
  locations under different custodians.
- The Wakir Phase-1a convention does **not** use a SLIP-39 passphrase.
  The security boundary is physical custody of the share artefacts.
  A passphrase can be added in Phase-2+ if the custody model changes.
- Share artefacts MUST carry a Wakir generation-id (the persona role,
  the issuance date, the SLIP-39 identifier). The generation-id is
  the operator's hook for verifying that a recovery-attempt set of
  shares all came from the same issuance — SLIP-39 does not catch
  cross-generation mismatches by itself in the extendable-flag mode.

### 3.2 Library posture

We adopt the SatoshiLabs reference implementation
[`shamir-mnemonic`](https://pypi.org/project/shamir-mnemonic/) (MIT)
rather than re-implementing SLIP-39. The reference library is published
by the spec authors and matches the spec by construction; the
re-implementation surface (GF(256) polynomial arithmetic, RS1024
checksum, 1024-word lexicon, group/member two-level split) is non-
trivial and error-prone.

The library README warns that its implementation is **not side-channel
hardened**. For the Wakir Phase-1a use-case (offline recovery
ceremonies, single-use, no online attacker on the same host) this is
acceptable. A hardened replacement is on the Phase-2+ backlog and
would be gated by an ADR before any online or repeat-use deployment.

### 3.3 Recovery drill (quarterly cadence)

Per consensus marker D-2 the operator runs a recovery drill once per
quarter. The drill validates that the live share inventory still
reconstructs the master secret with one share simulated as lost.
Implementation lives in `recovery_drill.simulate_recovery`.

The drill is an in-memory simulation; physical-presence verification
of the share artefacts is the operator's responsibility and runs
*before* the drill. The drill does not consume randomness, does not
rotate keys, and does not produce any artefact other than a
`RecoveryDrillResult`. The result is suitable for direct inclusion in
a WAT (Wakir Audit Trail) leaf so that successive drills are
publicly verifiable as having been performed.

Drill cadence schedule (Wakir convention):

| Quarter | Drill date (target) | Owner |
|---|---|---|
| Q1 | first business day in January | Treasury custodian |
| Q2 | first business day in April | Treasury custodian |
| Q3 | first business day in July | Treasury custodian |
| Q4 | first business day in October | Treasury custodian |

A missed drill is an audit finding (the internal-audit role's audit
sample MUST flag gaps > 100 days between successive drills).

## 4. Signature formats

### 4.1 AIP document signature

The signing pre-image is computed by:

1. Deep-copy the document and remove the `document_signature` field.
2. Canonicalise with RFC 8785 JCS (`rfc8785.dumps`).
3. Hash with SHA-256.

The signing key is the persona's Ed25519 master (or a delegated
sub-key). The signature is 64 raw bytes, encoded as 128 lowercase hex
chars in the output block:

```json
{
  "alg": "Ed25519",
  "kid": "biscuit-root-1",
  "signature": "<128-hex-char>"
}
```

`kid` defaults to `biscuit-root-1` to match the first entry of the
generator's `public_keys` array. The block is assigned by the caller
into `aip_doc["document_signature"]`.

Verification reverses the procedure: strip the `document_signature`
slot from the candidate document, recompute the pre-image, and verify
the signature byte-string against the supplied Ed25519 public key.

A signature mismatch returns `False`. Format violations (wrong algorithm,
malformed signature length, wrong key length) raise `ValueError` so
callers can distinguish "structurally broken" from "cryptographically
wrong".

### 4.2 DID document proof

DID-Core does not mandate a self-signature on the document itself —
integrity in the standard `did:web` flow is delegated to the publishing
HTTPS chain. For Wakir we additionally publish an internal proof so
audit and OTS-anchor consumers can verify document provenance without
trusting the publication HTTPS chain alone.

The proof block follows a Wakir-flavoured subset of the W3C Data
Integrity profile, scoped to the `EcdsaSecp256k1Signature2019` suite:

```json
{
  "type": "EcdsaSecp256k1Signature2019",
  "verificationMethod": "did:web:.../keys-secp256k1-1",
  "alg": "ES256K",
  "signatureHex": "<128-hex-char r||s>"
}
```

Signing procedure:

1. Deep-copy the DID document and remove the `proof` field.
2. JCS-canonicalise.
3. SHA-256.
4. ECDSA over secp256k1, signature returned in compact `r || s`
   encoding (32 bytes each, 64 bytes / 128 hex chars total).

Note: ECDSA over secp256k1 in `cryptography` uses a random nonce, so
two signatures over the same payload differ byte-for-byte. Both are
valid; equality of payload-binding is verified by cross-verifying
both signatures against the un-modified document.

### 4.3 Tamper-detection guarantees

In both formats, the signature pre-image is the *document body minus
the signature/proof slot*. Any modification to any other field
invalidates the signature. The placeholder content of the signature
slot at signing time does not influence the produced signature — this
is asserted by tests in `test_aip_signing.py`.

## 5. Open items (Phase-2+ tracking)

- Wakir-native DID method (`did:wakir`) — requires an ADR before
  spec work begins. Until then, `did:web` is canonical.
- Persona-Identity-Registry (V-907) — depends on ADR-0031-D4
  resolution; not in Phase-1a scope.
- Side-channel-hardened SLIP-39 — gated by ADR; required before any
  online or repeat-use deployment of the cold-storage primitive.
- Multi-group SLIP-39 layouts (e.g., a 2-of-3 group of (2-of-3) for
  9-share scenarios) — supported by the reference library, exposed
  by `split_master_secret` only via the single-group convenience
  surface. Multi-group access lives behind a Phase-2 helper.
